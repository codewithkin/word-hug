# System: Internationalisation

**Owner of:** i18next configuration, key naming conventions, locale detection and override, and the boundary between translatable UI and untranslatable content.
**Status:** Draft

---

## 1. The honest framing

There are two different problems here and the original spec conflated them.

| Problem | Solved by i18n? |
|---|---|
| Buttons, labels, celebration copy, shop descriptions, error messages | **Yes** — this is exactly what react-i18next is for |
| Puzzle content | **No** — the mechanic depends on English compound morphology |

`thunderstorm` is one word in English. *Tormenta eléctrica* is two words in Spanish with no shared prefix. Translating the answer word produces non-words (`truenofuego`). See `plans/00-spec-critique.md` §2.

**Therefore:** build the i18n layer properly and completely in v1, but do not enable a locale until a natively-authored puzzle bank exists for it. Settings offers only locales returned by `content.availableLocales()`. Shipping a Spanish UI around English puzzles would read as broken software.

**v1 status: English only. Spanish is deferred to v2** (`plans/99-backlog.md`). With one locale available, the Settings language control renders nothing and onboarding has no language step. The architecture is present and tested; it simply has one entry.

Building the layer now with a single locale is still the right call — it costs little, it forces the no-literal-strings discipline that makes v2 cheap, and retrofitting i18n into a finished app is far more expensive than starting with it.

## 2. Setup

```
apps/native/lib/i18n/
  index.ts        // i18next init
  detect.ts       // device locale detection + MMKV override
  locales/
    en.json
```

```ts
i18n.use(initReactI18next).init({
  resources: { en: { translation: en } },
  lng: resolveLocale(),          // MMKV override ?? device locale ?? 'en'
  fallbackLng: 'en',
  compatibilityJSON: 'v4',
  interpolation: { escapeValue: false },   // RN does not need HTML escaping
  returnNull: false,
});
```

**Initialised in `+loading`**, synchronously, before any screen mounts. Translation JSON is bundled — there is no async resource loading and therefore no flash of untranslated content.

### Locale resolution order

1. `wh.prefs` → `locale` (explicit user override in Settings)
2. Device locale via `expo-localization`, matched against available locales
3. `en`

A locale is "available" only if both a translation file **and** a puzzle bank exist for it.

## 3. Key conventions

Nested, namespaced by domain. Keys describe *where and what*, never the English text.

```json
{
  "common": { "continue": "Continue", "notNow": "Not now", "cancel": "Cancel" },
  "daily": {
    "title": "Today's hug",
    "prompt": "What word connects these three?",
    "wrong": "Not quite — try another",
    "soClose": "So close!"
  },
  "solve": {
    "celebration": ["Lovely.", "There it is.", "Beautifully done."]
  },
  "nudge": {
    "category": "The missing word is {{category}}.",
    "firstLetter": "The missing word starts with {{letter}}.",
    "coins_one": "{{count}} Nudge Coin",
    "coins_other": "{{count}} Nudge Coins"
  },
  "category": {
    "weather": "a type of weather",
    "material": "a material",
    "animal": "an animal"
  },
  "streak": {
    "current_one": "{{count}} day",
    "current_other": "{{count}} days",
    "broken": "Your streak rested. Today's a lovely day to begin again."
  },
  "shop": { "bundleTitle": "The Hug Bundle" },
  "settings": { "language": "Language", "sound": "Sound", "haptics": "Haptics" },
  "error": { "notFound": "This hug doesn't exist" }
}
```

Rules:

1. **No literal user-facing strings in components.** Enforced by an ESLint rule (`i18next/no-literal-string`) on `apps/native/app/**` and `apps/native/components/**`.
2. Keys are stable. Changing copy edits the value, never the key.
3. Pluralisation uses i18next suffixes (`_one`, `_other`) — never manual `count === 1` branching, which breaks in languages with more plural forms.
4. Interpolation for all dynamic values. Never string concatenation.
5. `category.*` keys are referenced **by the puzzle data** (`Puzzle.category`), so the content validator checks that every category key resolves. This is the one place content and translation files are coupled.

---

## 4. Copy tone constraints

The translation file is where the product's voice actually lives. Binding constraints on every string:

- No exclamation-heavy urgency, no all-caps, no countdowns
- Wrong-answer copy is neutral and encouraging, never corrective
- Streak-break copy is warm and forward-looking, never loss-framed
- Notification copy is invitational ("Today's puzzle is waiting"), never guilt-framed ("Your streak ends in 2 hours")
- No competitive language: no "beat," "win," "lose," "fail," "rank"

Any translator, present or future, gets these constraints as part of the brief. Tone does not survive a literal translation.

---

## 5. Formatting

- **Dates** (archive calendar, stats) via `Intl.DateTimeFormat` with the active locale — never manual formatting
- **Numbers** via `Intl.NumberFormat`
- **Prices** always from `storeProduct.priceString` (RevenueCat) — never formatted by the app, so currency and regional conventions are correct for free
- **RTL** — not required in v1 (no RTL locale planned), but avoid hardcoded `left`/`right` in styles; use `start`/`end` so RTL is not a rewrite later

---

## 6. Switching at runtime

- `i18n.changeLanguage(locale)` — react-i18next re-renders subscribed components, no restart
- Persist the choice to `wh.prefs.locale`
- Re-render must be verified on every screen, including ones behind navigation state
- Changing locale does **not** change the puzzle bank in v1 (only `en` exists). When a second bank ships, changing locale must also swap the daily schedule — which means solve history is per-locale and streaks would need a decision. Flag as a v2 problem, do not solve it now.

---

## 7. Adding a locale later

1. Author a native puzzle bank in `packages/content/src/puzzles/<locale>/` — **not a translation**
2. Add `apps/native/lib/i18n/locales/<locale>.json`
3. Brief the translator with §4 tone constraints
4. Run the content validator against a lexicon for that language
5. The locale appears automatically in Settings once both exist

Steps 1 and 5 are the expensive ones. Step 2 is the cheap one the original spec assumed was the whole job.

---

## 8. Testing requirements

- Every key in `en.json` is referenced somewhere (dead-key check in CI)
- Every `t()` call resolves to an existing key (missing-key check in CI)
- Pseudo-locale test: render every screen with strings inflated ~35% to catch layout breaks before a real translation does
- Every screen renders at the largest Dynamic Type setting with the pseudo-locale — this is the real check
- Missing-key fallback never displays a raw key to the user
